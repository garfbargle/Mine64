# Building and deploying

## Toolchain

Mine64 builds against a modern compatibility environment, not the original
proprietary SDK: the `mips-n64-*` cross compiler, NuSystem, libultra, libcart,
`spicy` and `makemask`, assembled from the public
[ModernN64SDKArchives/n64sdkmod](https://github.com/ModernN64SDKArchives/n64sdkmod)
archive by [`docker/N64SDK.Dockerfile`](../docker/N64SDK.Dockerfile) and
installed under the historical compatibility root `/etc/n64`.

Build the image once:

```sh
docker build --platform linux/amd64 -t mine64-nusys-build:local -f docker/N64SDK.Dockerfile .
```

`linux/amd64` is required — the archived host tools are amd64 binaries. Docker
Desktop handles this on Apple Silicon.

## Build the ROM

```sh
docker run --rm --platform linux/amd64 -v "$PWD:/work" -w /work mine64-nusys-build:local make -j2
```

Output is `build/mine64.n64`. With your own compatible SDK installed, set
`ROOT=/etc/n64` (or your compatibility root) and just run `make`.

`generate_assets.py` runs automatically and produces the tile set and UI font;
no Minecraft assets are involved. `toolchain/spicy-ld.sh` bridges the historical
makerom flags and compiler-runtime objects to modern GNU ld.

| Variant | Command | Notes |
| --- | --- | --- |
| Release (default) | `make` | Non-debug NuSystem/libultra |
| SDK debug | `make DEBUG=1` | Unoptimized; objects cached separately, so switching is safe |
| Audio | `make AUDIO=1` | Writes `build/mine64-audio.n64`, leaving the silent ROM in place |

Runtime audio is deliberately absent from the stable ROM. The audio variant
uses full-size NuSystem command buffers, explicitly aligned VADPCM books, and
starts the audio manager only after flashcart storage initialisation. Music
waits for a number of rendered frames before its first ROM DMA, so a scheduler
failure is distinguishable from a boot or storage failure.

## Deploy to a SummerCart64

**Turn the N64 off before any SD write.** While the console runs it owns the
cartridge SD card and USB writes are rejected as locked.

Persistent install, the recommended path:

```sh
./perma-load
```

Verifies the SD card is initialised and the console is powered off, builds the
ROM, writes it to the cart's menu path, and verifies the stored file. Turn the
N64 on afterward and pick Mine64 from the SummerCart64 menu. `SC64_DEPLOYER`
and `SC64_SD_PATH` override the deployer location and menu path.

Development loop — uploads to the cart's temporary ROM RAM, no SD write:

```sh
./live-load
```

Both scripts wrap `sc64deployer`, expected at
`../N64FlashcartMenu/tools/sc64/sc64deployer` unless `SC64_DEPLOYER` says
otherwise. The equivalent raw commands are `sc64deployer sd upload
build/mine64.n64 <menu path>` and `sc64deployer upload build/mine64.n64`; add
`--direct` to the latter to bypass the bootloader.

Saves live on the cartridge SD card when libcart detects a supported flashcart.
The filename rules and filesystem constraints are strict and have silently
broken saving before — see *Save format* in [Internals](internals.md).

## Assets

### Textures

Tiles are generated by `generate_assets.py` as CI4 textures. Export the current
art for a viewer or paint workflow:

```sh
python3 tools/export_textures.py
```

That writes a native atlas, a nearest-neighbour preview, and a JSON of tile
order and palette metadata into `art/`.

To import your own art, put an edited atlas PNG at `art/custom-textures.png`;
`make` converts each cell to a CI4 tile with nearest sampling and a per-tile
palette. Ore, bedrock and mossy variants are generated as companions, so the
editable atlas stays small. Cell order and the full walkthrough:
[Custom texture workflow](custom-textures.md).

> Regenerating assets means running `make`, not `generate_assets.py` alone —
> running the script by itself drops the custom atlas and the build can't
> notice.

### Music

The audio ROM consumes N64-ready assets checked into `assets/audio/` (VADPCM
music, big-endian PCM effects, decoder metadata headers in `assets/`). No
private WAV masters or user-specific paths are needed to build.

To replace the tracks, re-import masters inside the same Docker environment:

```sh
docker run --rm --platform linux/amd64 -v "$PWD:/work" -v /path/to/music:/music:ro -w /work \
  mine64-nusys-build:local make music MUSIC_SOURCE_DIR=/music
```

The pipeline downmixes to mono, resamples, filters inaudible content,
normalises, and encodes VADPCM, replacing the checked-in payloads and metadata
headers. Intermediates stay in `build/audio-import/`. `MUSIC_RATE` and
`MUSIC_LOWPASS` trade ROM size for clarity and should be set together;
`MUSIC_EFFECTS=` keeps the input's level and EQ untouched. Review and commit
the encoded assets whenever masters or settings change.

Music playback is not linked into the default ROM — validate with the `AUDIO=1`
build so a known-good silent ROM always remains at `build/mine64.n64`.

### Sound effects

```sh
make sfx
```

Generates the short original effects deterministically via
`tools/generate_sfx.py`, writing N64 PCM inputs to `assets/audio/sfx/` (local
WAV previews there are ignored). Commit the PCM inputs and metadata header
after regenerating.

## Tools

### Offline model preview

Every model is untextured boxes and quads through `guRotateRPY` and
`guPerspective`, none of which needs an N64. `tools/preview` reads the vertex
data, joint offsets and angle defines straight out of the source and rasterises
here, so the picture cannot drift from the game:

```sh
tools/preview/mob.py pig --strip head-turn
tools/preview/hand.py iron_sword --reach 0.5
```

It answers where a part ends up, what occludes what, and whether the framing
works — not how fast it runs. Reference: [Offline model preview](offline-preview.md).

### Emulator screenshots

`tools/emu` drives mupen64plus (`brew install mupen64plus`) through a
replacement input plugin that replays a written timeline of controller states,
so a run needs no keyboard or window focus and lands on the same screens every
time:

```sh
tools/emu/run.sh tools/emu/scripts/gui-tour.txt
```

One labelled PNG per `shot` in the script lands in `build/shots`.

Emulation is only good for interface layout, and model questions are answered
faster by the preview above. It flatters the GUI — a clean digital framebuffer
has none of the composite blur or overscan a real TV adds — frame pacing is not
representative, and the faults in [Hardware notes](hardware.md) do not
reproduce. Legibility, performance and RDP work belong on hardware. Script
grammar and frame-timing rules: [Emulator screenshots](emulator-screenshots.md).
